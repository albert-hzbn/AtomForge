\chapter{Installation, builds, and troubleshooting}\label{ch:install}
\section{Running a packaged desktop build}
Extract a complete package into a writable folder and run \code{AtomForge} (\code{AtomForge.exe} on Windows, \code{AtomForge/bin/AtomForge} on Linux). Keep the native libraries beside it: \code{atomforge\_science\_native}, \code{atomforge\_electronic} and spglib (\code{symspg}), which the Python package in \code{AtomForge/python} also uses. Structure files are read and written by AtomForge itself; no Open Babel installation is needed. To open structures at launch, pass their paths (wildcards such as \code{*.cif} are expanded). The same program is the command line: given a mode such as \code{--build}, \code{--pipe} or \code{--science} it runs without a window (Chapter~\ref{ch:python}).

The desktop draws through wgpu, which uses Direct3D~12 or Vulkan on Windows, Vulkan or OpenGL on Linux and Metal on macOS, whichever the graphics driver offers. If the window fails to render, check the graphics driver and whether a remote or virtual session supplies one of these; \code{--renderer opengl} (with Mesa's software rasteriser on Linux) usually works there.

\section{Choosing the renderer}\label{sec:renderer}
\ui{Settings > Renderer} chooses the graphics interface (Automatic, Vulkan, Direct3D~12, Metal or OpenGL, as the platform offers); the choice is saved as \code{renderer=} in \code{\textasciitilde/.atomforge\_preferences.txt} and applies at the next start, and the menu shows the interface in use. For one run, start AtomForge with \code{--renderer vulkan}, \code{opengl}, \code{dx12} or \code{metal}, or set the environment variable \code{ATOMFORGE\_RENDERER}; the command line takes precedence over the environment, which takes precedence over the saved choice. Every interface shows the same scene, previews and exports.

Structures of up to five million atoms open for editing; larger files open as atom clouds (Section~\ref{sec:large-datasets}), which stream from disk and draw a level-of-detail subsample within point and memory budgets.

\section{Build requirements}
AtomForge is written in Rust and builds with Cargo (Rust 1.85 or newer, installed with rustup) and the platform's linker: the MSVC Build Tools with the Windows SDK on Windows, GCC or Clang on Linux. Every library is a Rust crate that Cargo fetches on the first build, except spglib: the Windows build uses the copy in \code{rust/crates/af-spglib/vendor}, Linux links the system's \code{libsymspg} (\code{libsymspg-dev}). On Linux the window also needs the X11 or Wayland and xkbcommon development packages. See the repository's \code{INSTALL.md}.

\section{Building}
\begin{lstlisting}
cd rust
cargo build --release -p af-app -p af-ffi-science -p af-ffi-electronic
cargo test --workspace --release
cd ..
python rust/tools/run_ui_tests.py
\end{lstlisting}
The program is \code{rust/target/release/AtomForge} (\code{AtomForge.exe}). The tests compare the scientific results with reference outputs of the earlier C++ implementation, most of them bit for bit; \code{run\_ui\_tests.py} drives the desktop through scripted sessions (\code{rust/tests/ui}) and writes screenshots to \code{rust/target/ui}, and \code{rust/tools/run\_python\_suite.sh} runs the Python package's tests against the native libraries. Close a running AtomForge before rebuilding, because Windows locks the executable.

\section{Portable packaging and CI}
\code{python rust/tools/package.py} builds in release mode and writes \code{AtomForge-<version>-win64.zip} or \code{AtomForge-<version>-linux-x86\_64.tar.gz} to \code{rust/target/package}, with the program, its libraries, the Python package, the manual and the examples. Validate the extracted package in a clean environment and test an actual structure import, not only process startup.

When a CI job fails, inspect the first failing step and its log: dependency download, compilation, linking, tests, or packaging. The last generic failure line is usually less informative than the first error.

\begin{samepage}
\section{Reporting a reproducible problem}
Record the application commit, operating system, build options, input/import settings, selected fields, exact steps, and error text. Supply a small reproducer with expected and observed behaviour. For numerical issues include geometry, units, and integrals; for visual issues capture the entire dialog.
\end{samepage}
